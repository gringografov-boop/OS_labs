# Лабораторная работа №2 — вариант 5

Обмен между отдельными программами `parent` и `child` через два неименованных канала. Реализация на C++17: общая логика использует собственный интерфейс `os`, а системные вызовы вынесены в `common/code/os/os_posix.cpp` и `os_win.cpp`.

## Условие

Первая строка ввода — имя выходного файла. Родитель передаёт его ребёнку аргументом командной строки, а последующие строки с числами — через первый pipe, связанный со стандартным вводом ребёнка. Ребёнок проверяет число: составное записывает в файл, простое или отрицательное завершает обработку. Через второй pipe он возвращает статусы, чтобы родитель тоже остановился. Исходное условие: предоставленная методичка «Лабораторные работы №2», группа вариантов 1, вариант 5.

Дополнения для случаев, не определённых условием:

- `0` и `1` не записываются; обработка продолжается.
- Пустые строки, текст, несколько чисел в строке и выход за диапазон `int` отклоняются; можно ввести следующее число.
- EOF завершает обработку; родитель закрывает входной канал и дожидается ребёнка.
- Файл создаётся или обнуляется при запуске ребёнка, ещё до ввода первого числа.
- Проверка простоты выполняется только в дочернем процессе. Родитель не анализирует число.

## Сборка из корня

Нужны CMake 3.16+ и компилятор C++17. Для автотестов дополнительно нужен Python 3.

Linux:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
./build/bin/lab2/parent
```

Windows, PowerShell с доступным MSVC Build Tools или Visual Studio:

```powershell
cmake -S . -B build
cmake --build build --config Debug
chcp 65001
.\build\bin\lab2\parent.exe
```

`chcp 65001` нужен при вводе русских имён файлов: интерфейс `os` принимает пути в UTF-8, а Windows-реализация вызывает Unicode-функции `CreateProcessW` и `CreateFileW`.

Можно собрать только лабораторную, не подключая остальные компоненты репозитория:

```bash
cmake -S lab2 -B build-lab2 -DCMAKE_BUILD_TYPE=Debug
cmake --build build-lab2 --config Debug
```

Тогда исполняемые файлы появятся в `build-lab2/bin/lab2/`. Каталог вывода одинаков для Debug и Release. `parent` и `child` должны лежать рядом. Путь к `child` определяется относительно самого `parent`, а не текущей рабочей папки.

## Пример

Ввод:

```text
result.txt
4
6
9
17
```

Содержимое `result.txt` после завершения:

```text
4
6
9
```

Число `17` простое, поэтому оно не записывается и оба процесса завершаются. Относительный путь к файлу считается относительно папки, из которой запущен родитель.

Не следует направлять результат в один из исходников или исполняемых файлов: выходной файл открывается с обнулением.

## Обмен данными

```text
parent -- pipe1: строка с числом + '\n' --> child stdin
parent <-- pipe2: однобайтовый статус -- child stdout
                                           |
                                           +--> выходной файл
```

| Статус | Значение |
|---|---|
| `R` | Файл успешно открыт, ребёнок готов принимать числа |
| `W` | Составное число записано |
| `I` | Число 0 или 1 пропущено |
| `E` | Некорректная строка или выход за диапазон int |
| `S` | Получено отрицательное или простое число; обработка завершена |

Статус `R` — начальное подтверждение готовности, а не ответ на число. После него на каждую строку приходит ровно один статус. Каждый статус немедленно сбрасывается через `flush`. Диагностика ребёнка идёт в `stderr`, чтобы не смешиваться с протоколом `stdout`.

При системной ошибке выводится сообщение в `stderr`, а процесс возвращает ненулевой код. Родитель также проверяет код завершения ребёнка. Частичные записи обрабатываются циклом `WriteAll`. На Linux прерванные системные вызовы чтения/записи повторяются, `SIGPIPE` преобразуется в обрабатываемую ошибку записи.

## Платформенный слой

`FileHandle` и `ProcessHandle` — непрозрачные типы интерфейса преподавателя. В этой реализации за ними находятся собственные маленькие структуры: `int fd`/`pid_t` на Linux и `HANDLE` на Windows. Их нельзя самостоятельно приводить к `int` или `HANDLE`: используются только функции `os`.

`UniqueFile` владеет файловым ресурсом и вызывает `os::CloseFile` при выходе из области видимости. Дескриптор процесса закрывается после `WaitProc`. На Windows дескриптор главного потока закрывается сразу после создания процесса — сам поток при этом продолжает работу.

Linux использует `FD_CLOEXEC`: после `dup2` ребёнку доступны стандартные потоки, а исходные концы pipe закрываются при `execv`. Внутри `CreateProc` есть дополнительный временный служебный pipe: через него родитель узнаёт об ошибке подготовки/`execv`. Это не третий канал обмена числами; после успешного запуска он закрывается.

Windows использует `STARTUPINFOEXW` и явный список наследуемых дескрипторов: ребёнку передаются только дубликаты нужных стандартных потоков. Обоснование механизма: [документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

Из C++ используются строки, контейнеры, потоки консоли и RAII. `std::thread`, `std::filesystem`, высокоуровневые библиотеки запуска процессов, `system()` и `popen()` не применяются. Выходной файл открывается и записывается через системный API.

## Автотесты

Из корня проекта после сборки:

```bash
python3 lab2/tests/test_lab2.py build/bin/lab2/parent
```

Windows:

```powershell
python lab2/tests/test_lab2.py build/bin/lab2/parent.exe
```

Тесты запускают настоящие процессы во временных папках: составные и простые числа, отрицательные значения, 0/1, EOF, ошибки ввода, пределы `int`, длинные строки, пути с пробелами, Unicode, отсутствие дочернего файла и ошибки открытия выходного файла. Linux дополнительно проверяет ошибку формата исполняемого файла.

Отчёт в эту поставку не включён и будет подготовлен отдельно.
